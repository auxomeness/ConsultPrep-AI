# ConsultPrep AI — Phase 10 demo checklist

Use invented details only. This checklist reproduces the current frontend, not a patient-record or clinician workflow.

## Preflight

- [ ] Use the final committed `frontend` branch. From `frontend`, run `npm run lint`, `npm run typecheck`, `npm run test:run`, `npm run test:e2e`, and `npm run build`. Record any QA-001 worker failure even if a retry passes.
- [ ] If attempting live AMD output, supply `RADEON_API_KEY` and `RADEON_MODEL` through the approved local environment. Verify a synthetic smoke turn before the audience arrives. Neither setting was available on the Phase 10 verification host; its start request returned 503.
- [ ] Open the local app and confirm the homepage and `/intake` load. Use a fresh browser profile with no saved demo conversations.
- [ ] Keep a copy of this checklist and the final quality report visible to the presenter. Do not use real patient details.

## Reproducible audience sequence

1. Open `/`. Show “ConsultPrep AI,” “AI documents. Clinicians decide.”, the single “Begin intake” action, and its small demo/safety note.
2. Activate **Begin intake**. Point out the visible development-demo notice: made-up information only; no patient record or clinician handoff.
3. Type a synthetic concern such as “I would like to discuss a made-up headache that began this week.” The composer rejects empty or whitespace-only text.
4. If AMD preflight succeeded, send the concern and show the actual returned follow-up. The working text appears only while the request is pending. Describe this as a demo AI response, not a diagnosis.
5. If AMD is unavailable, show the actual error and preserved editable text. Do not describe a mocked response as live AMD output. For a predictable fixture demonstration, run the named Playwright test `synthetic API responses render the question, original answer, and follow-up` and disclose that the response is intercepted synthetic test data.
6. When a follow-up is available, enter another made-up answer. If the service supports a summary in the configured run, open **Review summary**, inspect the source text, and label any confirmed state **not submitted**. Do not rely on this step without a successful preflight.
7. Open `/intake/states` separately. Explain that its Reported, Unknown, Not answered, Unclear, and Conflicting examples are synthetic; show that both conflict statements remain visible and Unknown is not denial.
8. Open `/intake/review` separately. Explain that it is independent of the conversation and was not generated by AI. Open and close a source disclosure, show the response ID and original wording, then show the correction beside the earlier statement. Point out unavailable correction/confirmation controls.
9. State that there is no clinician UI, patient-record save, submission, or clinician finalization to demonstrate. Member 2 schema and authorization tests are preparation, not a runnable case workflow.

## Failure and recovery fallback

- A missing AMD configuration produces a 503; the UI retains the synthetic draft so it can be retried after configuration is fixed. Avoid repeated live calls when the service is down.
- If the production build hits QA-001, report the failure and retry once; keep the first output. A later success does not close the defect.
- If a browser test response is used instead of AMD, say “mocked API response for UI verification.” The separate review and information-state routes are fixture screens, not live intake results.
- If the demo cannot load the local app, use the already verified synthetic screenshots or this report only as labeled fallback evidence; do not claim an interactive run occurred.

## Final spoken limitations

“ConsultPrep AI organizes information before a professional consultation. It does not diagnose, prescribe, or replace clinical judgment. This is a development demo; use made-up information. Browser-device conversations are not patient records. The review examples are synthetic, and no clinician has reviewed or finalized them.”
